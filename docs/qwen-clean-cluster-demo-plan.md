# Qwen encrypted-storage demo: clean-install runbook specification

**Status: planned acceptance procedure, not an executable installer today.**
The new `confidential-inference-pattern` repository and the `demo-*`/`release-*`
Make targets below must be implemented by the
[implementation plan](confidential-inference-pattern-plan.md). They are shown as
the intended user interface so a different implementer can build and test the
same outcome. Do not run them against the current CoCo repository expecting them
to exist. Ordinary `oc` inspection commands are identified separately.

## Demo outcome

Starting with an installed, qualified CoCo Validated Pattern and **no previous
demo resources**, install the separate inference add-on repository and demonstrate:

- Qwen3-0.6B served by KServe in a stock confidential GPU VM.
- Verified encrypted model disk from the internal OCI registry, populated into
  a fresh Block PVC and mounted read-only at `/model`.
- A separate initially blank Block PVC formatted inside the TEE as LUKS + keyed
  dm-integrity + ext4 and mounted read-write at `/data`.
- Standard Trustee release rules requiring approved CPU/GPU evidence and workload
  identity. The additional storage authority controls lifecycle authorization.
- An unprivileged stock vLLM container, a privileged trusted guest sidecar, and
  a browser chat interface sending requests to that exact KServe backend.
- A fresh VM successfully reopening the same data, without another format/import.

The existing lab uses `/models/qwen`; the new generic profile uses `/model` after
the compiler/policy changes in the plan. The model files remain plaintext only in
the trusted publishing environment and the authorized guest/GPU execution path.
The PVCs, registry and importer carry ciphertext.

## Demo identities and prerequisites

Use a unique non-secret run ID such as `qwen-demo-001`; derive names from it. The
run ID is durable input, not a timestamp regenerated by every retry. Refuse a
fresh-install test if that run's claims, authority record or keys already exist.
Use `resume` for an interrupted run and `reopen` for retained-data tests.

| Input | Generic requirement | Existing edge example |
| --- | --- | --- |
| Base | Healthy compatible CoCo VP and stock runtime | OCP 4.22.15, OSC 1.13.0; exact pins in release lock |
| Runtime | Qualified confidential CPU + confidential GPU profile | `kata-cc-nvidia-gpu`, SNP + NVIDIA RTX PRO 6000 |
| Serving | Existing compatible KServe, or explicit install-if-absent | Existing controller v0.20.0 |
| Capacity | One available confidential GPU plus approved pod/VM resources | Historical working VM: 8 vCPU, 64 GiB; tune only with a new approved profile |
| CSI | Block, RWOP, compatible transport/topology | `lvms-vg1`, Immediate; model 2 GiB, data 1 GiB |
| Registry | Internal OCI endpoint, CA and bounded push/pull identities | `https://image-registry.openshift-image-registry.svc:5000` |
| Model | Pin revision and every required file; no runtime download | `Qwen/Qwen3-0.6B`, revision `c1899de289a04d12100db370d81485cdf75e47ca` |
| Trusted services | Reachable standard Trustee, scoped secret backend, authority and approval signer | Reuse trusted lab services only after ownership/compatibility checks |
| Client | Browser route or port-forward; explicit transport boundary | VPN NodePort is an optional site override, not a generic default |

A clean test on the existing server needs free capacity. The current two GPUs are
occupied; the runbook must not stop either existing Qwen service automatically.
Use a spare GPU/cluster or an explicitly scheduled replacement test window.

Preflight must test guest-network reachability to existing Trustee/registry endpoints;
test a newly installed authority endpoint before release authorization. Check
certificate chains, time synchronization, required external collateral services
or approved cached collateral, and the actual CSI binding mode. It must not
invent host measurements or use `curl -k` as an attestation/TLS workaround.

## Stage 0 — install and inspect the separate repository

Proposed interface after the new repository is implemented:

```bash
git clone <new-confidential-inference-pattern-repository>
cd confidential-inference-pattern
git checkout <reviewed-release-tag>
# Credentials are already available through the operator's private environment.
./pattern.sh make demo-preflight VALUES=overrides/sites/my-site.yaml RUN_ID=qwen-demo-001
./pattern.sh make install-addon VALUES=overrides/sites/my-site.yaml
```

Expected output: an installation inventory listing reused services, new add-ons,
required trusted integration and unsupported combinations. The installer creates
its own root Argo Application/AppProject in the existing GitOps instance. It does
not bootstrap another CoCo pattern, edit firmware, replace Kata or take over
existing Trustee/KServe resources.

Real inspection commands that already exist:

```bash
oc get clusterversion
oc get runtimeclass
oc get storageclass
oc get crd inferenceservices.serving.kserve.io
oc get crd confidentialvolumes.storage.confidentialcontainers.org
oc get crd confidentialworkloads.storage.confidentialcontainers.org
oc get crd encryptedmodelsources.storage.confidentialcontainers.org
```

**Gate:** all selected profile prerequisites pass; new controllers are healthy;
admission is installed before privileged helper permission. Record baseline
UIDs/readiness of unrelated workloads for the non-disruption check.

## Stage 1 — prepare a new encrypted model release

Run publication in a **trusted producer environment**, which may be external to
the workload cluster. It needs plaintext model access, the specific model key,
private scratch, pinned publisher tools and registry push access. Qwen is public,
so an HF token is not required by this release; gated models add a producer-only
credential. Do not pass a literal KBS URI as a Hugging Face token.

Proposed interface:

```bash
./pattern.sh make release-publish VALUES=overrides/sites/my-site.yaml \
  MODEL_RELEASE=qwen3-0.6b-v1
```

The command resolves credentials through the configured trusted backend; private
values are not command-line arguments. The operation must:

1. Download the pinned source or use a verified offline source bundle.
2. Create/reuse the model-release credential with explicit create-only/CAS semantics.
3. Build the LUKS2 encrypted ext4 image; add dm-verity over the header/ciphertext.
4. Reopen and check all model hashes and rejected writes in the trusted producer.
5. Publish only the encrypted disk and public metadata; verify the returned OCI
   manifest digest and retain an immutable reference against registry pruning.
   When the trusted producer cannot reach the internal `.svc` address, a restricted
   upload job may receive the ciphertext/public metadata only. It needs registry
   push access, not model decryption credentials; the trusted process checks its
   resulting digest against the prepared artifact.
6. Emit a public release receipt containing source revision, file inventory, disk
   size/digest, OCI digest, LUKS/header identity and verity geometry/root.

**Gate:** a fresh encrypted artifact is verified, no plaintext/key-bearing files
are present in its layer, and the public source/manifest is complete. A public
descriptor remains a candidate until independently authorized.

To avoid turning every persistence test into a model download, the harness also
supports an explicitly selected existing approved immutable model release. The
first full clean-install acceptance run must exercise publication itself.

## Stage 2 — create and populate fresh claims

Proposed interface:

```bash
./pattern.sh make demo-provision VALUES=overrides/sites/my-site.yaml \
  RUN_ID=qwen-demo-001 MODEL_RELEASE=qwen3-0.6b-v1
```

Generated model claim structure (illustrative names, no copied lab UIDs):

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: qwen-demo-001-model
spec:
  storageClassName: <qualified-block-class>
  volumeMode: Block
  accessModes: [ReadWriteOncePod]
  resources:
    requests:
      storage: 2Gi
  dataSourceRef:
    apiGroup: storage.confidentialcontainers.org
    kind: EncryptedModelSource
    name: qwen-demo-001-model
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: qwen-demo-001-data
spec:
  storageClassName: <qualified-block-class>
  volumeMode: Block
  accessModes: [ReadWriteOncePod]
  resources:
    requests:
      storage: 1Gi
```

`EncryptedModelSource.spec` is generated from the verified producer receipt. It
pins the repository, manifest digest, disk digest and length. The populator creates
a prime claim, imports ciphertext, flushes/read-verifies it, removes the importer
and rebinds to the target. The RW claim has no `dataSourceRef` and no host format job.

Real observation commands, using the namespace selected by site values:

```bash
oc get encryptedmodelsource,pvc,pod -n confidential-inference
oc get confidentialvolume,confidentialworkload -n confidential-inference
```

The binding job reads actual claim UIDs and creates immutable CVs. For example:

```yaml
apiVersion: storage.confidentialcontainers.org/v1alpha1
kind: ConfidentialVolume
metadata:
  name: qwen-demo-001-model
spec:
  claimRef: {name: qwen-demo-001-model, uid: <resolved-live-uid>}
  access: ReadOnly
  profile: luks-verity-v1
  initialization: {policy: Never}
  keyResource: kbs:///default/model-keys/qwen3-0-6b-v1
  content:
    approvedManifestRef: qwen3-0-6b-v1
---
apiVersion: storage.confidentialcontainers.org/v1alpha1
kind: ConfidentialVolume
metadata:
  name: qwen-demo-001-data
spec:
  claimRef: {name: qwen-demo-001-data, uid: <different-resolved-live-uid>}
  access: ReadWrite
  profile: luks-integrity-v1
  initialization:
    policy: OnceIfApproved
    filesystem: ext4
    owner: {uid: 1001, gid: 1001}
  keyResource: kbs:///default/model-keys/qwen-demo-001-data
```

The `approvedManifestRef` resolves through the trusted release/authority process;
creating a similarly named ConfigMap does not approve the model. These references
are identifiers, not secret values.

**Gate:** the model target is Bound to the expected source/transport digest;
prime/importer handoff completed; RW claim is provisioned but uninitialized;
CVs pin the correct UIDs. With delayed binding use the qualified placement phase,
otherwise preflight must reject that class instead of waiting forever.

## Stage 3 — declare the workload and approve its release

The workload chart renders a CW with one application and binding intent:

```yaml
apiVersion: storage.confidentialcontainers.org/v1alpha1
kind: ConfidentialWorkload
metadata:
  name: qwen-demo-001
spec:
  template:
    metadata:
      name: qwen-demo-001
      annotations:
        serving.kserve.io/deploymentMode: Standard
    spec:
      predictor:
        annotations:
          storage.confidentialcontainers.org/bindings: >-
            [{"volume":"model","confidentialVolume":"qwen-demo-001-model",
              "container":"kserve-container","mountPath":"/model"},
             {"volume":"data","confidentialVolume":"qwen-demo-001-data",
              "container":"kserve-container","mountPath":"/data"}]
        containers:
          - name: kserve-container
            image: <approved-stock-vllm-image-by-digest>
            # Reviewed startup waits for storage, performs self-tests, then serves /model.
            # Full resources, security context and startup arguments come from the profile.
```

This is abridged proposed YAML: `/model` and generic profile handling need the
implementation work. A new installation omits `adoptExistingUID` entirely.

Proposed trusted release commands:

```bash
./pattern.sh make release-prepare VALUES=overrides/sites/my-site.yaml RUN_ID=qwen-demo-001
./pattern.sh make release-authorize VALUES=overrides/sites/my-site.yaml RUN_ID=qwen-demo-001
./pattern.sh make demo-wait VALUES=overrides/sites/my-site.yaml RUN_ID=qwen-demo-001
```

`release-prepare` collects the controller request and renders a deterministic
public package. `release-authorize` executes in the trusted environment: enroll
the model manifest and first-use RW identity, create/verify scoped backend keys,
apply the exact Trustee identity rules through its existing owner, verify the
loaded configuration, then sign/publish the deployment approval. It may require
explicit approval or a preauthorized release rule; never approve arbitrary claims.

**Gate:** the controller reports approved configuration applied, then KServe and
the application separately become Ready. The former is not proof of the latter.
No hand edits to the InferenceService, copied prior signature or guest-image rebuild.

## Stage 4 — prove first use and real inference

The measured startup/self-test must produce structured evidence before vLLM starts:

| Check | Required evidence |
| --- | --- |
| Fresh guest / stock components | New pod/VM identity, selected runtime, stock boot artifacts and pinned vLLM image |
| CPU and GPU authorization | Verified fresh attestation result, expected identity/InitData, valid GPU appraisal and bound GPU evidence |
| Read-only model | Expected manifest/file hashes; RO/nodev/nosuid/noexec mount; write attempt fails |
| New RW first use | Authority initialization events occur once; approved LUKS/integrity profile and ext4; UID/GID 1001 can write |
| Durable marker | App writes run/release ID plus random nonce under `/data`, fsyncs file and directory; expected nonce/hash retained outside the guest as public test evidence |
| Application isolation | Non-root, drop ALL, NoNewPrivs, read-only rootfs; no raw storage device, API token, authority credentials or private key socket |
| GPU execution | CUDA operation on the expected confidential GPU; vLLM loads the model from `/model`, with no model download fallback |

Proposed validation command:

```bash
./pattern.sh make demo-test VALUES=overrides/sites/my-site.yaml RUN_ID=qwen-demo-001
```

The harness sends a random synthetic prompt through the chat API, checks the
response and vLLM success-counter increment, and follows Service/EndpointSlice
target UIDs to the exact confidential predictor pod. It checks both direct KServe
API and chat paths. Arbitrary real user prompts are not collected as evidence.

Real browser access for the default ClusterIP service, once installed:

```bash
oc -n confidential-inference port-forward service/qwen-demo-001-chat 8765:8080
```

The new chart must expose a stable named service port matching this documented
command. Browse `http://127.0.0.1:8765`. A VPN NodePort/site Route is optional;
the harness reports its actual URL instead of embedding the edge IP in code.

Presenter sequence: show ciphertext source and two Block claims; show the
declarations and attestation verdicts; ask the model a question; show which pod
handled it and which mounts it uses; show that administrator exec is denied.
Do not print keys, dump tokens, or relax guest policy to inspect the demo.

## Stage 5 — replace the VM and prove persistence

Proposed interface:

```bash
./pattern.sh make demo-restart VALUES=overrides/sites/my-site.yaml RUN_ID=qwen-demo-001
./pattern.sh make demo-test VALUES=overrides/sites/my-site.yaml \
  RUN_ID=qwen-demo-001 MODE=reopen
```

Record the old pod/VM UID, stop only this generated workload and wait for clean
mount removal/mapper close/authority release. Let the controller/KServe recreate
it. Require a new pod/VM UID, the same PVC UIDs and the same model artifact.

The new VM must read the old nonce/hash rather than overwrite it as if fresh,
append a new counter entry and fsync, then serve a second real prompt. Assert no
new initialization/format event and no second model import. Restart the controller
and populator and repeat an unchanged GitOps sync; record unchanged keys,
authority generation and PVC identity.

Also test deletion/recreation of the generated InferenceService while CW remains,
using the same valid approval. A time-limited approval needs renewal for later
recreation. Expiry does not evict a running VM or revoke already-released keys.

**Gate:** persistence and reconciliation pass without manually resetting the
authority. If stale Kubernetes objects block GC, record an infrastructure failure;
do not hide administrative cleanup inside a passing unattended test. Unexpected
shutdown retains ownership until an independently justified recovery procedure.

## Stage 6 — negative tests on isolated disposable resources

Never corrupt the successful demo's model or data PVC, replace a shared Trustee
policy, or switch a shared physical GPU out of CC mode for these tests.

| Test | Expected failure / proof |
| --- | --- |
| Wrong transport digest | Importer fails; target never handed off as populated |
| Altered ciphertext/header on a disposable copy | Integrity/header checks fail; vLLM never starts |
| Old model manifest/release | Authority rejects stale generation/release according to enrolled policy |
| Unapproved workload image/command/InitData | Approval or key release denied; no serving fallback |
| Missing/invalid GPU evidence | Profile/authority/Trustee deny; real-hardware negative fixture must be isolated; no permissive test switch in production policy |
| Invalid/expired deployment signature | Controller refuses new deployment/recreation; existing-running behavior reported separately |
| Wrong RW key or nonblank unregistered disk | Refuse initialization/open; never erase or regenerate a key |
| Simultaneous RW consumer | Storage/controller/authority reject second ownership; no multi-writer claim |
| Host-visible secrets | Controller/importer cannot read volume keys; application cannot use private key service; scans find no credentials in release artifacts |
| Administrator exec | Guest agent denies `ExecProcessRequest` in both vLLM and helper |

A CPU/GPU policy unit test supplements, but does not replace, the required real
attestation and key-release evidence. Whole-volume RW rollback is outside the
current guarantees unless independently protected authority state and an epoch
protocol are implemented and tested.

## Repetition, cleanup and evidence

The harness must provide separate explicit modes:

- `fresh`: new run ID, new claims/data key/authority enrollment; optionally reuse
  an existing immutable model release only when requested.
- `resume`: same inputs and run ID after interruption; compare retained identities
  and continue from the last durable step without re-encryption/reformatting.
- `reopen`: preserve all disks/keys, replace only the workload VM and verify data.
- `stop`: close volumes and stop this workload; retain its claims, keys and history.
- `destroy`: explicit destructive request for this run, after clean closure and
  a retention decision; never the default behavior of uninstall/prune.

For every run, write a public JSON result and a human-readable report including
exact release/profile/version pins, phases, identities, attestation checks,
population and initialization counters, inference traces, persistence and negative
test outcomes. Print an explicit `PASS`, `FAIL` or `BLOCKED` for every gate.
Do not infer success from Argo Healthy, Bound PVCs or log messages alone.

The final walkthrough must be executed by a second operator/model using only the
new repository, documented inputs and authorized credentials. If it requires old
private scratch, a captured lab UID, an undocumented manual patch or a custom
Kata/vLLM build, the clean-install deliverable is incomplete.
